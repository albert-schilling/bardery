# Software factory: scientific papers from 2026 (research, 2026-11-03)

> **Snapshot from 2026-11-03, a companion to [the software factory research note](2026-10-21-software-factory.md).** Most of these are arXiv preprints that haven't been peer reviewed; a venue is named only where I confirmed it. Read the linked abstract before relying on a number.

**Method:** arXiv API queries over cs papers submitted 2026-01-01 to 2026-11-03 on eleven topics (software factories, harness engineering, maintainability of agent code, automated code review, `AGENTS.md`/context files, productivity, agent-written tests, spec-driven development, agentic software engineering, agent-authored pull requests, human-in-the-loop), 339 unique results. I read the abstracts of the 64 that looked relevant and kept 58. Commissioners come from the papers' author blocks on arXiv. Google Scholar couldn't be queried automatically, so papers published only in ACM or IEEE libraries are underrepresented; a web search found MSR '26 papers, all also on arXiv. Two study protocols without results ([2609.04208](https://arxiv.org/abs/2609.04208), [2606.25257](https://arxiv.org/abs/2606.25257)) are left out.

**Tags:** `factory` · `economics` · `maintainability` · `context-files` · `harness` · `tests` · `review` · `oversight` · `humans` · `industry` (data from a company's own systems).

## What the evidence says for Bardery's factory

1. **Instructions are weak; checks and prohibitions work.** Context files barely change success ([2602.11988](https://arxiv.org/abs/2602.11988), [2607.27250](https://arxiv.org/abs/2607.27250)). Helpful rules are prohibitions ([2604.11088](https://arxiv.org/abs/2604.11088)). Compiled checks beat prompts ([2603.00822](https://arxiv.org/abs/2603.00822)). Security "do not"s in prose aren't enforced ([2608.23550](https://arxiv.org/abs/2608.23550)). Supports a short `AGENTS.md`, conventions as lint rules and hooks, and "don't" rules over "do" rules.
2. **Instruction files decay and grow.** Agents follow stale files over the code ([2610.30571](https://arxiv.org/abs/2610.30571)), files triple in size ([2608.11095](https://arxiv.org/abs/2608.11095)), 23% reference deleted code ([2606.09090](https://arxiv.org/abs/2606.09090)). Write the reason next to each rule (Bardery's convention already does in comments), check instruction files for staleness, and re-test and retire rules ([2610.32578](https://arxiv.org/abs/2610.32578)).
3. **Unattended agents add lasting complexity**, with or without speed gains ([2601.13597](https://arxiv.org/abs/2601.13597), [2604.03035](https://arxiv.org/abs/2604.03035), [2606.21804](https://arxiv.org/abs/2606.21804)), and less where teams commit AI configuration ([2608.25241](https://arxiv.org/abs/2608.25241)). Measure complexity per PR (the quality ratchet).
4. **Agent tests are weak** (mutation scores under 60%, 80% without real assertions, more mocks): measure with mutation testing and assertion checks; give the test-writer the test-to-code map, not TDD procedure ([2603.17973](https://arxiv.org/abs/2603.17973)).
5. **Review agents help but don't replace humans yet**: a third to 72% of known bugs found, much less on complex or context-heavy changes. **Risk-graded automation works at scale** (Meta: a third the reverts, a fiftieth the incidents). Review loops need stopping rules ([2609.10123](https://arxiv.org/abs/2609.10123)); reviewer findings need verification ([2603.00539](https://arxiv.org/abs/2603.00539)).
6. **Agents don't know when to ask or when not to act** ([2604.09408](https://arxiv.org/abs/2604.09408), [2605.07769](https://arxiv.org/abs/2605.07769), [2610.36346](https://arxiv.org/abs/2610.36346)). Your stop-and-ask factory must enforce stops in the workflow, give "no change needed" as a valid result, and give groomers a stopping criterion.
7. **Independent verification matters**: reward hacking spreads between agents and is reduced by separate verifiers ([2610.12822](https://arxiv.org/abs/2610.12822)).
8. **Protect human understanding** ([2601.20245](https://arxiv.org/abs/2601.20245), [2610.37888](https://arxiv.org/abs/2610.37888)): reading design discussions and code explainers keeps the reviewer able to review.
