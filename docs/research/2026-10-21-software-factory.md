# Software factory: what others do and what Bardery lacks (research, 2026-10-21)

> **Working notes, started 2026-10-21, input for #34.** Updated as each author is researched. Tools and repos in this field change weekly; check the linked sources before relying on a detail.

## Bardery today

What the repo already has that a factory builds on:

- **Decision record:** grilling sessions (Q1–Q93), ADRs, a PRD with ordered slices, `CONTEXT.md` as the glossary. Agents read them before designing.
- **Skills:** Matt Pocock's set in `.agents/skills/` (linked from `.claude/skills`), including `grill-with-docs`, `to-spec`, `to-tickets`, `triage`, `implement`, `implement-spec`, `wayfinder`, `tdd`, `code-review`, `pr`, `retro`, `improve-codebase-architecture`.
- **Mechanical checks:** oxfmt, type-aware oxlint (with layer and import rules tested by `layers.test.ts`), lefthook on staged files, CI checks, Terraform plan on pull requests, deploy to staging from `main`, an image test.
- **Small PRs:** one issue per PR, about 300 lines, tests with every change, screenshots of UI changes.
- **Learning loop:** [`harness-log.md`](../harness-log.md). Each PR records what the agent got wrong and the harness change that prevents it, preferring a check over a sentence.
- **Review:** an agent implements, a human reads every PR line by line (walking skeleton PRD), and Copilot reviews.

How it runs: interactive, one agent session at a time, the human starts every step.

## Expectations for Bardery's factory (from the user, 2026-10-21)

- Not a dark factory, and not line-by-line review either: the factory keeps producing and **stops the line the moment it needs steering**. Agents never silently assume a requirement or convention: they may suggest, but they stop and ask, then record the decision so the same question isn't asked twice.
- The factory improves itself: friction is logged and turned into checks, steps or conventions right away.
- `AGENTS.md` is an index of links to topic files (Nx, tests, naming, …), read on demand. Context-efficient, but the agent must still reliably read what applies.
- Every PR improves non-functional quality. Problems outside its scope are surfaced as labelled issues for an agent to pick up, not fixed in passing.
- An orchestrator skill or agent hands phases to sub-agents: planner (checks the plan is sound and current), implementer, several reviewers that commit their findings. A light orchestrator with strong planner and reviewers, and a medium implementer.
- Groomers on a schedule, each with one job: delete unused code, judge test quality, survey architecture and file issues, enforce naming and structure.
- Liked from Dodds: short `AGENTS.md`, the `friction` label with automatic issues, one command that runs what CI runs.
- A test-writer sub-agent writes tests from the spec before implementation and saves a **test plan** (acceptance criterion → test) in the issue. After implementation it checks whether the code went further than the tests and adds tests. The implementer may not edit tests; if it thinks one is wrong, it stops and asks.
- Regenerated docs (Tielke) on a schedule that fits the throughput, at least weekly. A comment checker runs on changed files only, not the whole codebase, because a sweep would be slow and miss the reasons behind comments.
- Tidying: a PR may tidy the code it is about to change, in its own structural commit before the behaviour change (Beck's _Tidy First?_). Everything else it notices is filed as an issue.
- The issue and the PR hold the factory's state: plan, test plan, decisions, review findings. Phases and sub-agents read and write there, not in a session's memory.
- A **Trust Factory** (Beck's term) or **Quality Factory**: the factory produces trust and quality explicitly, not only features.

## Where Bardery deliberately differs

These are choices, not gaps. Each is a decision for #34's grilling.

- **Planning docs are kept.** Pocock throws planning docs away after implementation so stale ones can't mislead agents, and treats closed issues as the record. Bardery keeps grilling records, ADRs and PRDs as the decision record. The risk is stale docs; Dodds handles it with weekly doc gardening.
- **Every PR is read by a human.** Pocock and Dodds reserve human review for one-way doors. StrongDM forbids human review. Bardery reviews every line for now (walking skeleton PRD). Moving away from that is the biggest step.
- **Glossary name.** Bardery uses `CONTEXT.md`; Pocock's skills now call it `GLOSSARY.md`.
- **Agent-agnostic durable knowledge.** Dodds puts all product knowledge in the repo so any agent can pick it up; Bardery does the same.

### Kent C. Dodds

- **Thesis:** engineers become "software factory engineers" who build the factory, especially the primitives that let agents verify their own work. What stays human is judgment: product engineering, choosing the right target ("Building the right thing is more important than building the thing right"). He agrees with Warp's "factory engineers" memo but pushes back where it treats the product as optional: factory efficiency only helps if the right work enters the factory.
- **Fifteen principles for shipping unread agent code** (MEGA session, 2026-09-30): verification over authorship; product understanding first; align before implementing; keep moving up the abstraction ladder; knowledge in the repo; agents log friction, a scheduled agent fixes it; document primitives and grade risk by which ones a change touches; prefer reversible decisions (flags); schedule deletion (legacy reaper); automate in stages (by hand, then agent, then deterministic code); separate implementers and reviewers; tests from the implementer are a weak signal, layer AI review, CI, previews, flags, tested DR; measure value, not cost; human value is judgment.
- **Kody's repo as the reference:** [kentcdodds/kody](https://github.com/kentcdodds/kody) applies this in the open.
  - `AGENTS.md` is a ~20-line index, capped in CI by a "slop ratchet".
  - One principle per page under `docs/principles/`, each with a "when to open it" line.
  - `docs/contributing/harness-engineering.md`: when a mistake repeats, encode it in the cheapest guardrail that works: lint, types or `validate` first, then tests, then scripts, then docs. "If reviewers repeat the same comment twice, encode it." Weekly doc and quality gardening.
  - `npm run validate` is the single local gate, matching CI.
  - The `ship-pr` skill grades risk: low merges on green CI; medium waits for Bugbot; high also waits for CodeRabbit and Devin and is parked unless the agent has merge authority. It loops on CI and review bots with wake timers, and reviewers must scrutinise assertions changed in the same PR as the code.
  - The `friction` label: agents file durable, recurring papercuts as issues, and a daily sweep fixes them.
  - Cloud agents (Cursor, Devin) work against PR previews when local can't exercise a change.
- **Kody, the product:** a sandboxed cloud runtime where agents write and run code, with a secrets vault agents can use but not read, and packages with their own DB, jobs and webhooks. He calls it a "personal software factory"; he reports 122 PRs in 24 hours from his factory (podcast, unverified).

Sources: [15 principles (MEGA)](https://mega.dev/ship-without-reading-the-code), [Introducing Kody](https://kentcdodds.com/blog/introducing-kody-your-personal-software-factory), [kody repo](https://github.com/kentcdodds/kody), [The Last Software Engineer](https://gitnation.com/contents/becoming-product-engineers), [What the devil is a Factory Engineer?!](https://kentcdodds.com/calls/01/08/what-the-devil-is-a-factory-engineer), [Warp memo coverage (Latent Space)](https://latent.space/p/software-factories).

### Birgitta Böckeler (Thoughtworks, martinfowler.com)

She writes for people _using_ coding agents, from small experiments, and is careful to state limits. She doesn't write about "software factories" by name.

- **Mental model** (_Harness engineering for coding agent users_, 2026-04-02): Agent = Model + Harness. Controls are **guides** (feedforward: AGENTS.md, skills, conventions) or **sensors** (feedback: types, linters, tests, review agents), and each is **computational** (deterministic, cheap, run on every change) or **inferential** (LLM review or judge: semantic, slower, probabilistic). Guides alone never learn whether they worked; sensors alone let the agent repeat mistakes.
- **Three harnesses:** maintainability (easiest, mature tools), architecture fitness (fitness functions, e.g. performance tests), behaviour ("the elephant in the room": AI-written tests checking AI-written code isn't enough).
- **Timing:** fast checks before commit; expensive ones (mutation testing, broad architecture review) after integration; drift sensors (dead code, test quality, dependencies) and runtime sensors outside the change flow, on a schedule.
- **Steering loop:** when an issue recurs, improve a guide or sensor. Agents can write the structural tests, rules and custom linters. "Harnessability": strong types, clear module boundaries and few, fixed topologies make a codebase easier to harness (Ashby's law: fewer topologies, less variety to control).
- **Human role:** a harness directs human input to where it matters; it shouldn't aim to remove it.
- **Maintainability sensors experiment** (2026-05-19 to 27, TypeScript/Next.js app):
  - File and function rules (max lines, function length, arguments, complexity) caught agent failures well but are **off in ESLint's default preset**. A custom formatter replaced messages with fix guidance and an allowed escape hatch ("raise the threshold slightly, but only as the rare exception"); agent suppressions became a good starting point for review.
  - dependency-cruiser layer rules replaced a markdown structure guide; their messages restate the layering. Limited to imports, names and folders.
  - Raw coupling data didn't help the AI judge; an **AI modularity review** (Vlad Khononov's Modularity Skills) worked best, as "garbage collection" on a schedule. Run it more than once: a second run found new issues. Without it the agent "was definitely compounding inadvertent technical debt."
  - **Coverage misleads:** a file at 100% statement coverage had 13 surviving mutants (Stryker). Mutation testing on changed code is her measure of test strength.
  - **Agents skip guide-only checks:** she had to ask "many, _many_ times" why the agent hadn't run the sensors. A pre-commit hook or agent hook forces them. Her `sensors` CLI runs all sensors and gives the agent a short summary with the trend against a snapshot.
  - Too many sensors risk "feedback overload" and over-engineered refactorings; sensors can conflict (max-lines pushed complexity into long prop chains).
- **TDD in the agent loop** (2026-08-10, small informal experiment): agent-run TDD gave no better solutions and no better mutation scores, cost 3–8.5× the tokens, and often fixed the design too early. Agents faked or skipped red. She has **stopped telling agents to do TDD**; she measures outcomes instead (mutation testing, static analysis, modularity reviews, trends such as files touched per change) and suggests **Approved Scenarios**: humans approve functional scenarios, which are then frozen.
- **Context engineering** (2026-02-05): reusable prompts are instructions (do a task) or guidance (conventions). Who loads context is the LLM (skills, unreliable), the human (slash commands) or the software (hooks, deterministic). Build context up gradually; prune instructions models no longer need; don't copy large instruction sets from elsewhere. "Illusion of control": every instruction is still interpreted.
- **Related on the same site:**
  - Kief Morris, _Humans and Agents in Software Engineering Loops_ (2026-03-04): humans _out of_, _in_ or **_on_ the loop**. "On the loop" means fixing the harness that produced a bad artefact, not the artefact. The "agentic flywheel": agents propose harness improvements; adopt in stages, reviewing proposals, then backlogging them, then auto-applying above a risk threshold.
  - Naresh Jain, _Are Harnesses Worth the Cost?_ (2026-10-13): a behavioural harness cost a frontier model 7× more with no gain, and took a cheaper model from 3/10 to 10/10 accepted runs. "What changes with model capability is not whether independent sensors are needed, but when they run."

Sources: [Harness engineering for coding agent users](https://martinfowler.com/articles/harness-engineering.html), [Maintainability sensors for coding agents](https://www.martinfowler.com/articles/sensors-for-coding-agents.html), [TDD inside the agent loop](https://martinfowler.com/articles/exploring-gen-ai/tdd-in-the-agent-loop.html), [Context engineering for coding agents](https://martinfowler.com/articles/exploring-gen-ai/context-engineering-coding-agents.html), [Humans and agents in software engineering loops](https://martinfowler.com/articles/exploring-gen-ai/humans-and-agents.html), [Are harnesses worth the cost?](https://martinfowler.com/articles/are-harnesses-worth-the-cost.html), [Exploring Gen AI series](https://martinfowler.com/articles/exploring-gen-ai.html).

### David Tielke (independent architect and trainer, .NET enterprise)

He writes for enterprise teams with high quality demands, mostly in German YouTube videos. These notes come from the auto-generated German transcripts of two videos.

- **The experiment** (_Der Moment, der die Softwareentwicklung geändert hat!_, 2026-06-21): he rebuilt his 18-year-old back-office app alone in 45 working days, with Codex first and then almost only Claude Code. Scope: 10 microservices behind an API gateway, n8n workflows, three clients, a local LLM behind an MCP server for an agent (Hermes). Output: 213 user stories, 4,083 acceptance criteria, 420k lines, 2,900 API tests plus 392 workflow tests, 85% coverage on critical paths, "0% structural debt", 1,300 pages of docs. He compares this with two client teams' estimates (about 19 person-years) and gets a factor of 93, which he lowers himself to 60 or 25. It's one self-reported experiment; the teams estimated in a day. Tokens: 27 billion (mostly cache reads), covered by two Claude Max plans (about €1,620).
- **Spec vs harness:** two separate folders. The **specs** say _what_ to build (stories, acceptance criteria). The **harness** says _how_: architecture, coding rules, testing, environments. Neither is mixed into the other.
- **Computational sensors at scale:** an architecture guideline of **880 rules** taken from a client project, checked by NDepend, plus a full C# and Blazor coding guideline checked by ReSharper. After every change the agent runs them. He stopped reading the code because the tools proved the structure matched his rules; the worst code he saw was a "2" on the German school scale.
- **Harness Correction Development:** when output deviates, fix the harness, not the code, so the deviation can't recur. In the earlier video he calls the same idea **Context Correction Development**: after each feature, ask the agent which new patterns or decisions the session used that the context files don't describe yet, then update them (V1 → V2 → V3).
- **Five phases of his role:** micromanagement (developer) → quality-driven (harness and tools; architect) → spec-driven (the agent splits stories into tasks) → test-driven (product owner) → idea-driven and voice-driven (stakeholder: four hours of critical voice discussion with Claude on a drive, the agent pushing back with "remember that module does it like this").
- **Tests from acceptance criteria, before code.** A harness file defines how tests are structured and what to test. Tests come from the spec's acceptance criteria, not from the code: "otherwise the test just tests the code that was there." He tests only at the API and workflow level (each service with its own test DB, asserting responses, domain events and DB state; WireMock stands in for Office 365, Google and Trello), because those are what the agent will later depend on.
- **Docs regenerated every night** by Claude Code on the build server, so the developer handbook never drifts; he read the docs more often than the code.
- **Agent reach:** Docker locally, SSH to the test environment with nearly full rights, production logs read-only.
- **Four rules for client projects** (_Die Illusion von sauberem KI Code_, 2026-04-12):
  1. Don't let the agent generate the memory files (`/init`): they're superficial. Write them yourself, like a guideline for a human colleague.
  2. One session per feature; compaction makes the agent drift to other patterns and names.
  3. Context engineering: `AGENTS.md` is the **persistent context** and links to **dynamic context** (`arc.md`, `code.md`, UI/UX…) that the agent lazy-loads when the task needs it.
  4. Context Correction Development after each feature (above).
- **Caveat he states himself:** the result depends on decades of architecture experience. "AI is a great tool once you understand the basics of software development and architecture." Other teams he advises mostly ship code that is "functionally correct but structurally threatening."

### John Ousterhout (_A Philosophy of Software Design_)

Retired from Stanford; no talks or writing on AI coding of his own (his home page and book page show nothing after 2024). His value here is a **vocabulary and rubric for design quality**, which Pocock's `codebase-design` skill already builds on.

- **On AI** (Pragmatic Engineer interview, 2025-04-09): he doesn't see current tools replacing high-level design. The interviewer's framing: AI tools act like his "tactical tornadoes", fast output that leaves complexity behind, so design matters more as more code is generated.
- **Complexity** = dependencies + obscurity. Its symptoms: **change amplification** (a simple change touches many places), **cognitive load**, **unknown unknowns**. Complexity is incremental: no single change causes it, so it has to be fought in every change.
- **Strategic, not tactical programming:** invest roughly 10–20% of effort in design on every change. This is the per-PR quality ratchet (G16) in his words.
- **The 14 red flags** (book summary): shallow module, information leakage, temporal decomposition, overexposure, pass-through method, repetition, special-general mixture, conjoined methods, comment repeats code, implementation documentation contaminates interface, vague name, hard to pick name, hard to describe, nonobvious code. A ready-made checklist for a reviewer or architecture groomer; mostly inferential (LLM) checks, few are computational.
- **Deep modules:** simple interface, much hidden behaviour. "General-purpose modules are deeper" (somewhat general-purpose interfaces, special cases pushed out or hidden). **Pull complexity downwards** and **define errors out of existence**.
- **Design it twice:** sketch two radically different designs and compare before choosing. Cheap for a planner agent.
- **Comments:** interface comments and non-obvious reasons are essential; "the cost of missing comments is easily 10–100× the cost of incorrect comments." He recommends writing the interface comments **first**, before the implementation, as a design tool: if a comment is hard to write, the design is wrong.
- **Against over-decomposition** (debate with Robert Martin, 2024–25): "The One Thing approach is simply wrong in many cases." Splitting into many small methods creates "entanglement" and shallow methods. Martin: "we both value decomposition, and we both avoid entanglement; but we disagree on the relative weighting."
- **Against TDD**, for unit tests: TDD "forces thinking about the small details before thinking about the high-level design." He tests in larger units (a class, a few methods) and writes the failing test first only when fixing a bug. This agrees with Böckeler's experiment and disagrees with Pocock's `tdd` skill.
- **Agent skills built from the book** (community, not endorsed by him): [lukeramsden/software-design-agent-skill](https://github.com/lukeramsden/software-design-agent-skill), [ciembor/agent-rules-books](https://github.com/ciembor/agent-rules-books/blob/main/a-philosophy-of-software-design/a-philosophy-of-software-design.md).

Sources: [Pragmatic Engineer interview](https://newsletter.pragmaticengineer.com/p/the-philosophy-of-software-design), [APOSD vs Clean Code discussion](https://github.com/johnousterhout/aposd-vs-clean-code), [book page](https://web.stanford.edu/~ouster/cgi-bin/aposd.php), [home page](https://web.stanford.edu/~ouster/cgi-bin/home.php).

### Kent Beck (XP, TDD, _Tidy First?_)

He writes weekly at [newsletter.kentbeck.com](https://newsletter.kentbeck.com) (formerly tidyfirst.substack.com) about coding with "the genie", from his own sessions. A book, _Augmented Software Design: Taming the Genie_ (O'Reilly), is listed for September 2026; I couldn't confirm it has shipped.

- **Augmented coding vs vibe coding** (2025-06-25): "In augmented coding you care about the code, its complexity, the tests, & their coverage." His system prompt, published in the essay: work from a plan file of tests; on "go", implement the next unmarked test and only enough code to pass it; red → green → refactor; **Tidy First: never mix structural and behavioural changes in one commit, structure first, label each commit as one or the other**; commit only when all tests pass and all warnings are resolved.
- **Warning signs that the genie is off track:** loops; functionality nobody asked for, "even when it was a reasonable next step"; cheating, such as disabling or deleting tests. Two of his first three attempts collapsed under accumulated complexity until he steered the design closely. Result: correct and fast, but "not so good about the code quality".
- **TDD is a "superpower" with agents** because agents cause regressions (Pragmatic Engineer, 2025-06-11), yet he can't stop them "deleting tests in order to make them 'pass!'". He's experimenting with a TCR skill (test && commit || revert: failing changes are reverted automatically), 2026-04-01.
- **Genie tarpit** (2026-04-29): genies produce "a degraded facsimile of the mediocre code it trained on". Software has two axes: features (works now) and futures (can be changed safely). Neglecting futures doesn't show for a while, then "complexity piles on complexity until even the genie can't pretend to make progress any more." He admits nobody knows the fix yet.
- **Trust factory** (2026-06-02): "We're accumulating code faster than we are accumulating trust." XP was a system for manufacturing trust: programmer tests, pairing, CI, refactoring, observability. Solo work with a genie removes most trust-building interactions, and genies optimise for the prompt, not the purpose, and ignore optionality. He proposes slowing down deliberately: make sure it works, make structural improvements that keep options open, talk to people more, restate the long-term purpose regularly.
- **Code review with a genie** (2025-12-26): two purposes remain. **Intent:** "You asked for X. This code does Y. Are you sure?" **Structure:** "I'm maintaining it for future augmented me", because tangled code makes the AI err too.
- **Isolated auditor** (Genie Fight, 2025-09): a programmer genie tunes the code; an auditor genie in a separate repo and environment, unable to change code or talk to the programmer, pulls the latest commit, writes its own benchmarks and reports. Neither can fudge the other. An "editor" genie in the same setup deleted all the code, so isolation needs care.
- **Persona vs constraints** (2026-01-20): "code like Kent Beck" changed naming and test style but not the architecture; explicit constraints ("Use the Composite pattern") shaped the architecture. Combining both worked best. A reader's tip: distil the practices you want into a reviewed file instead of naming a person.
- **Multi-agent scepticism** (Nobody Wants Agents, 2026-04-23): with a coordinator/implementer/verifier tool he became "the manager of the swarm", holding state the system should have tracked. "Multi-agent is a feature; outcome orientation is the goal." He wants to state an outcome and have the tool say whether it's achievable and what it costs.
- **Other recent themes:** "features consume optionality", so alternate features and tidying; YAGNI is about timing, not cost; volatility (how often code changes) predicts where tidying pays.

### Dex Horthy (HumanLayer; "context engineering", Research-Plan-Implement)

The most experienced critic of software factories: he ran one and shut it down.

- **His lights-off factory** (July–November 2025): agents wrote, reviewed and deployed with no human reading the code. It grew to 30–40k lines, including an "insanely complicated state machine" of four processes talking over sockets, stdio and an event bus; one bug took weeks to trace; the codebase was archived. "If you let the agents take the wheel, this is what happens." Each slop pattern becomes precedent that later agents copy.
- **Why harnesses aren't enough** (_Why Software Factories Fail_, 2026-07-23): models are trained with RL to make tests pass, and nothing penalises coupling or poor design; a model works for minutes while bad architecture costs months. On judge models: "if the model knew what good code looks like, it would probably write it in the first place." His latest talk (2026-10-22): "There Is No Software Factory Without Better Verifiers."
- **Read the code; aim for 2–3×, not 10×.** "We're stuck reading the code for now. But we can still move pretty fast."
- **Instruction budget** (_Everything We Got Wrong About RPI_, 2026-03): frontier models follow about 150–200 instructions reliably, shared with CLAUDE.md, system prompt and tools. His 85-instruction planning prompt skipped "ask the user questions first" for about half of users unless they said "the magic words". Fix: split it into steps of under 40 instructions each: **questions → research → design → structure → plan → worktree → implement → PR** ("QRSPI"). "Don't use prompts for control flow if you can use control flow for control flow."
- **Research without the ticket:** one context turns the ticket into questions; a fresh context answers them without knowing the goal, so it reports facts about the code, not opinions.
- **Review short documents, then the code, not the plan.** A 1,000-line plan costs as much to review as the code and still diverges. Instead:
  - a **design discussion** (~200 lines): current state, target state, the codebase patterns it will follow (the chance to say "that's not how we do it here"), decisions, open questions;
  - a **structure outline**: "if the plan is the implementation, the outline is the C header files": signatures, new types, and **vertical slices** in order, each testable. Models otherwise write horizontal plans (all DB, then all services…).
  - "30 minutes over here in pre-planning and alignment can save you hours in review." His factory talk adds a product review (agreed behaviour, often mockups) first.
- **Harness techniques** (HumanLayer blog, 2026): CLAUDE.md under ~60 lines, written by hand (cites an ETH Zurich study that generated ones perform worse); conditional blocks such as `<important if="you are writing or modifying tests">`, because Claude Code tells the model the file "may or may not be relevant"; Stop hooks that are silent on success and return errors with exit code 2; sub-agents for context control with a defined return format, not job-title personas; persist decisions in documents instead of relying on compaction.
- **"Kill the pull request":** HumanLayer builds a collaborative IDE to steer agents in real time; HumanLayer core was open-sourced (Apache 2.0) on 2026-10-23, including its RPI skills.

Sources: [Everything We Got Wrong About RPI (YouTube)](https://www.youtube.com/watch?v=YwZR6tc7qYg), [Why Software Factories Fail (YouTube)](https://www.youtube.com/watch?v=Ib5GBkD555M) and [summary](https://finance.biggo.com/podcast/2a49159603eadab6), [AAIF article](https://aaif.io/blog/dex-still-thinks-long-running-coding-agents-stink), [BigGo article](https://finance.biggo.com/news/15099f5634f5ab9a), [Getting Claude to read your CLAUDE.md](https://www.humanlayer.dev/blog/stop-claude-from-ignoring-your-claude-md), [Skill issue: harness engineering](https://www.humanlayer.dev/blog/skill-issue-harness-engineering-for-coding-agents), [Open sourcing HumanLayer](https://www.humanlayer.dev/blog/open-sourcing-humanlayer).

### Gene Kim (_The Phoenix Project_, _The DevOps Handbook_; _Vibe Coding_ with Steve Yegge)

He brings the DevOps and flow view: what happens to the whole delivery system when coding gets cheap.

- **The bottleneck moves** (Coder blog on a podcast, 2026-07-23): when coding is cheap, the queue forms at review and oversight. Faros AI telemetry: teams that used AI most merged far more PRs, review time rose sharply, and company-level delivery metrics didn't improve. "Everybody's still standing in line, and your whole job as a leader is making sure nobody's waiting."
- **Architecture decides who benefits:** in Adidas's 750-person GenAI pilot, loosely coupled teams with fast feedback gained a lot; teams tied to the ERP with tight coupling and slow releases gained little. Agents bypass architectural boundaries and call undocumented interfaces; one AI-built codebase needed a two-day stand-down after two weeks. "The same instincts that served us at 5 miles per hour now fail us at 50."
- **_Vibe Coding_ (2025):** FAAFO, the value of AI coding: fast, ambitious, autonomous, fun, optionality. "Delegation of implementation doesn't mean delegation of responsibility" (the "head chef"). **Three developer loops** by timescale: inner (seconds to minutes), middle (hours to days), outer (weeks to months), each with prevent, detect, correct.
- **Failure patterns guide** (companion PDF), each with symptoms, immediate fix and prevention:
  - inner loop: **"tests are passing" lie** ("show me the test output"; never commit on the AI's claim), **context amnesia** (clear context at 50%), **instruction drift** (adds features nobody asked for; explicit acceptance criteria), **debug loop spiral** (more logging instead of root cause; limit debug attempts);
  - middle loop: **eldritch code horror** (critical: incomprehensible, everything connected; "if you can't understand code AI wrote, stop everything"; architecture reviews and "code elegance" checks after each session), **agent workspace collision**, **memory tattoo decay** (stale progress docs; date-stamp them, delete plans when done), **multi-agent deadlock**;
  - outer loop: **bridge torching** (critical: silently changed APIs; "you cannot break existing functionality", API compatibility tests in CI, accretion-only), **repository deletion**, **stewnami** (workspace chaos), **organizational process gridlock** (create a fast lane for low-risk changes; automate checks).
  - Universal emergency procedure: stop all agents, find which loop the problem belongs to, check version control, back up, simplest fix first, **document the incident for future prevention**.
- **Agents as specialists** (with Yegge, _2026: The Year the IDE Died_): many specialised agents (product, coding, review, testing, merging) rather than "the world's biggest ant"; the context window as a diver's oxygen tank. Trust: "To what degree can I predict how the other party will act and react?"
- **The Three Ways** (_The DevOps Handbook_): flow (make work visible, small batches, remove queues), feedback (find problems where they occur, stop and swarm), continual learning (turn local discoveries into global improvements). These map onto the factory: small PRs, sensors and stops, and the harness log.

### Taiichi Ohno (Toyota Production System)

Ohno (1912–1990) built the Toyota Production System; his book _Toyota Production System: Beyond Large-Scale Production_ (1978) is the source. Many sayings attributed to him are paraphrases, so the ideas below are cited from the Lean Enterprise Institute and secondary sources, not as his exact words.

- **Jidoka ("autonomation", automation with a human touch):** "providing machines and operators the ability to detect when an abnormal condition has occurred and immediately stop work" (Lean Enterprise Institute). It is one of the two pillars of TPS, with just-in-time. Origin: Sakichi Toyoda's loom that stopped itself when a thread broke, so one operator could watch many looms instead of one. "Jidoka highlights the causes of problems because work stops immediately when a problem first occurs."
- **The four steps:** detect the abnormality → stop → fix the immediate condition → investigate the root cause and install a countermeasure so it can't recur. The last two are people's work, because they need diagnosis and judgement.
- **Andon:** anyone on the line can pull the cord and stop it. Stopping is expected, not punished.
- **Poka-yoke (error-proofing):** make the mistake impossible or immediately visible instead of relying on attention. In software: types, lint rules, hooks that deny an action.
- **Standardised work and kaizen:** the current best way of doing a job is written down; only against a standard can a deviation be seen and an improvement measured ("where there is no standard, there can be no kaizen" is the popular paraphrase). Standards start lenient and are improved continually.
- **Five whys:** ask why until you reach a cause you can fix in the process.
- **Waste (muda):** overproduction, waiting, transport, over-processing, inventory, motion, defects. Mary and Tom Poppendieck's _Lean Software Development_ (2003) translates them to software: extra features, waiting, handoffs, relearning, partially done work, task switching, defects.
- **Applied to coding agents** (practitioners, 2026):
  - Mario Hayashi, _The Factory Must Grow III_ (2026-05): any worker that detects a systemic risk writes a "halt" verdict to a file and exits; the orchestrator locks that workflow and dispatches nothing until a human clears it. Also halts on a hook timeout, a missing verdict, an agent marking an issue done with no output, an empty diff. "Dead code beats limping code"; false-positive stops are cheap; agents pulled the cord several times in the first week and each investigation improved the system.
  - George Racu, _Jidoka for AI-assisted coding_ (2026-04-01): three "red light" stop conditions: an **explainability gap** (the developer can't follow the working solution), a **pattern fallacy** (a plausible pattern that breaks a domain rule), a **coverage illusion** (full coverage, edge cases and state changes unchecked). Keep "manual sprints" on critical logic so the reviewer keeps the skill to review.
  - `andon-for-llm-agents` (PyPI): maps abnormality to a failing exit code, test or build, and the line stop to blocking push, deploy and publish through agent hooks. I couldn't load its page to check the details.

Sources: [Lean Enterprise Institute: Jidoka](https://www.lean.org/lexicon-terms/jidoka/), [Hayashi: The Factory Must Grow III](https://dev.to/logicalicy/the-factory-must-grow-part-iii-stopping-the-ai-agent-production-line-toyota-style-19if), [Racu: Jidoka for AI-assisted coding](https://georgeracu.github.io/blog/articles/jidoka-for-ai-assisted-coding), [andon-for-llm-agents](https://pypi.org/project/andon-for-llm-agents/0.1.0/), [Shmula on Ohno and standard work](https://www.shmula.com/taiichi-ohno-standard-work-must-be-practical/9479/), [Lessons from Taiichi Ohno](https://www.antoinebuteau.com/lessons-from-taiichi-ohno/).

### The Claude Code team (Anthropic, claude.dev blog)

How the team that builds Claude Code runs its own factory. Claude writes about 90% of Claude Code's code; Anthropic's monorepo went from about 2,500 landed changes a day in May 2026 to over 30,000 in September.

- **Code review** (_How the Claude Code team does code review_, Addy Osmani, Morgan Westlee Lunt, Qing Wang, 2026-10-15):
  - **The reframe:** not "did a human read the code?" but "what could go wrong with this change, and which check, automated or human, is right to catch it?" Goal: most PRs merge with at most one human (the author), with no rise in reverts or incidents. Human time (approvals, comments, waiting) is the metric; revert and incident rate the guardrail.
  - **Results** (June–September): merged PRs more than doubled, reverts fell by over 40%.
  - **Before the PR:** Claude runs tests, build and lint; a second agent reviews the diff in a fresh context. "Verification matters most": give the agent something it can run and make it show the output. Boris Cherny estimates this makes results two to three times better.
  - **On every PR:** required CI; AI review (parallel agents hunt bugs, **verifier agents vote on each finding**, only survivors are posted, style and cleanup findings dropped after A/B tests), tagged **Important / Nit / Pre-existing** so old bugs aren't blamed on the author; a separate security review; **every finding must be answered** (fixed, or resolved with a reason) and open findings block merge; a merge queue re-runs checks on the latest main. Depth per repo: Quick, Standard or Deep.
  - **Risk tiers, set by the change, not the author** (a classifier): low (docs, copy, internal-only, additive behind a flag) needs no human once checks are green; medium needs one; high (billing, auto-updater, CI workflows, anything owners list as sensitive) needs two. **An agent's approval never counts as a person's.** The person who prompted an agent's PR is a required reviewer. Approvals cover one commit; new commits need re-approval.
  - **Convergence:** agent authors and reviewers can loop forever (one PR: 50+ overnight rounds; 59% of later findings were old code). Fixes: a cap of three rounds, then reconsider the approach; diff-only re-review; flag the class of bug so all instances get fixed; never repeat a finding. One-round passes rose from 65% to 78%.
  - **Improving the reviewer:** past incidents and reverts become an eval set, run daily; any change to prompts, tools or model that lowers the score is dropped. Every comment is sorted by its outcome (fixed, wrong, intentional, doesn't matter); noise costs more with agent authors because each nit triggers another round.
  - **After merge:** feature flags, internal use first, staged release channels, one-step rollback. "You land it, you own it."
  - **Where humans stay:** whether to build it at all; risky code; architecture others will copy; reading the evidence (test output, screenshots, findings); owning outcomes. Understanding a module comes from asking Claude for an explainer of that slice, not from reading trivial diffs.
  - **Instruction files:** a short `CLAUDE.md` that links out; a `REVIEW.md` per area, written by owners: what failure looks like there ("docs: it lies; config: it misroutes"), a cap on nits, paths to skip, file-and-line evidence required, a summary starting with a count.
  - **Their gap:** no circuit breaker yet that tightens approval when reverts or incidents rise. Recurring review comments are fixed at the source: a skill, a lint rule or `CLAUDE.md`.
- **Skills** (_How we use skills_, Thariq Shihipar, 2026-06-03): nine categories; **product verification skills** (drive the app, assert state) have the most measurable effect on quality, worth an engineer's week. A **Gotchas** section is "the highest-signal content in any skill", grown from real failures. Don't state the obvious; state the goal and constraints, not every step; `SKILL.md` as a hub pointing to files read on demand; the description says _when to trigger_, not what it is. Skills can register hooks for their session (`/careful` blocks destructive commands, `/freeze` blocks edits outside a folder). A PreToolUse hook logs skill usage to find skills that don't trigger.
- **Effort** (_Spending your effort_, Thariq Shihipar, 2026-09-25): effort is a dial for independent judgement and verification. Higher effort catches hidden edge cases (reproduce the bug first, randomised tests against a reference, confirm the tests fail on incomplete fixes) but doesn't fix a wrong approach. His loop: spec and interview (human), implement on low effort, review the gist, verify and test on high effort.
- **Cloud sessions** (Addy Osmani, 2026-10-06): one VM per task, a fresh branch, credentials outside the VM, network levels from none to full; routines started by schedule, HTTP or GitHub events push to `claude/` branches; `/autofix-pr` fixes failing checks and review comments and asks about architectural ones. Practices: one task per session; **name the proof in the prompt** ("run the suite 30 times"); agree and commit the plan first; commands in `CLAUDE.md`. Parallel sessions can't see each other, so split along file boundaries. A session that found a bug outside its task proposed the fix but left it alone and reported it.
- **Agent automations** (Lance Martin, CJ Avilla, 2026-10-08): scheduled agents with read-only sources, one write destination, a versioned config, memory the agent can't edit (preferences) and memory it can (state), a network allowlist and a spending cap per run. Rules: read from a bookmark, not a time window; **report a failed read as a failure, never as a quiet day**; re-check before acting; assert a status or drop it, never hedge.
- **Evals and hillclimbing** (Lance Martin, 2026-09-28): to improve prompts, skills or harness, split cases into train and test; keep a patch only if both improve; one patch per round aimed at a root cause; "never paste failures into the prompt"; audit the eval (grader errors, answers leaking through git history) before blaming the agent.
